# 已解密列表读取内嵌专辑封面 —— 可行性分析

> 分析日期：2026-11-19 ｜ 性质：技术方案评估，**未改任何代码**
> 标注约定：`【实测】`= 本机跑命令验证；`【静态】`= 读代码/依赖推断，未实跑。

## TL;DR

**可行，推荐做，但有明确的适用边界。**

项目里**已具备读取封面所需的全部能力，无需新增任何 Python 依赖**：内置 `ffmpeg.exe` 可从音频文件提取内嵌封面图（已实测 mp3/m4a/flac 均成功），PySide6 的 `QImage.fromData()` 可直接把提取出的图像字节转成可显示的缩略图（已实测）。当前缺的只是"何时读、怎么缓存、如何嵌入卡片"这三层工程代码。

需要提前接受的现实：并非每个文件都有内嵌封面。封面来源是解密后的音频文件——**只有 um 解密时保留了内嵌封面、或用户开了 `--update-metadata`（当前配置里已有「更新封面」选项，走联网）的文件才有图**；纯文本/无封面文件会走占位图。

## 一、现状梳理（这些代码已经决定了插入点）

| 环节 | 位置 | 与封面的关系 |
|---|---|---|
| 输出目录扫描 | `decrypted_interface.py::_scan_output` | 后台线程扫 `os.scandir`，一次取齐 `(path, size, mtime)`，按 mtime 倒序。**这是读取封面的最佳时机/数据载体**——可在此顺带取封面字节。 |
| 条目结构 | 同上，`items` 为 `(path, size, mtime)` 元组 | 要带封面需扩展元组或建旁路缓存；条目对基类不透明，扩展不破坏网格。 |
| 建卡 | `_make_card(item)` | 目前把 `(size, mtime)` 传给 `TaskCard(meta=...)`；加封面即多传一个 `cover=` 参数。 |
| 卡片 UI | `task_card.py::TaskCard` | 固定高 64px，横向布局：`MarqueeLabel`(文件名) + `CaptionLabel`(元信息) + 右侧徽章。**左侧没有图像位**，加封面要改布局、给 48~56px 见方留位。 |
| 懒加载 | `GridCardContainer` `lazy_fill=True` | 已解密页只物化视口内可见卡片——**天然适合封面场景**：只给看得到的卡片读图，千级文件不会一次性全读。 |
| 呈现动画 | `grid_card_container.py` | 淡入/脉冲只改 opacity，不改几何；封面作为卡片子控件不受影响。 |
| 已有开关 | `config.py::update_metadata` → um `--update-metadata` | um 侧"联网更新元数据和专辑封面"，默认「默认」三态。它是**封面来源的上游**，不是读取侧开关。 |

## 二、技术路线对比

| 方案 | 依赖成本 | 实测结果 | 优点 | 缺点 / 风险 |
|---|---|---|---|---|
| **A. 内置 ffmpeg 提取** ✅ 推荐 | **零新增依赖**（ffmpeg 已是内置工具且被打包内嵌） | 【实测】mp3/m4a/flac 内嵌封面均以 PNG 流成功提取；`QImage.fromData` 成功转 200×200 图并缩放到 48×48 | 复用现成能力；支持格式最广；打包无负担 | 每张卡要起一次 ffmpeg 进程，需懒加载+缓存兜住开销；无封面时 ffmpeg 报错，需用 `-map 0:v:0?` 静默 |
| B. 新增 mutagen 等纯 Python 库 | 需 `uv add mutagen` + 重打包 | 【静态】未安装、未验证 | 无进程开销，解析快；能读标签 | 引入新依赖与打包体积；加密/损坏文件可能抛异常需兜底；与"零新增依赖"原则相悖 |
| C. um `--update-metadata` 联网抓图 | 零代码依赖，但依赖网络 | 【静态】um 帮助确认有此选项 | 可补齐无封面的文件 | 联网、慢、有隐私/合规与失败重试问题；**与"读取文件内嵌封面"是两件事**——它是写入侧，可作为补充来源但不能替代读取 |
| D. 查同目录 cover.jpg/folder.jpg | 零依赖 | 【静态】`os.path` 即可 | 覆盖部分"外置封面"场景 | 只能读到与音频同目录、且命名规范的图；工具输出目录通常平铺，覆盖有限 |

**推荐：以 A 为主**；C 作为"封面来源"的可选上游（已有配置，无需新功能）；D 可作为无内嵌封面时的低成本兜底，是否纳入视取舍。

## 三、关键实证数据（本机验证）

```
【实测 1】ffmpeg 从带封面 mp3 提取 PNG 流
  ffmpeg -i tagged.mp3 -map 0:v:0 -frames:v 1 -f image2pipe -vcodec png pipe:1
  → exit 0, 609 字节 PNG；探测流显示 Stream #0:1 Video: mjpeg 200x200 (attached pic)

【实测 2】多格式（同一命令模板）
  mp3  → 609 B  ✅      m4a → 609 B  ✅      flac → 609 B  ✅
  ogg  → 生成测试样本时编码器不支持内嵌图（测试命令限制，非读取能力问题）

【实测 3】无封面文件
  ffmpeg -map 0:v:0 ... → 报错 "Stream map matches no streams"
  → 必须用 -map 0:v:0? 让无封面时静默成功（重要）

【实测 4】QImage 直接吃字节流
  QImage.fromData(QByteArray(png_bytes)) → OK, 200x200, Format_RGB32
  scaled(48,48) → QPixmap 非空 ✅
```

## 四、实现要点（若立项）

1. **读封面放在哪**：
   - 主推在 `_scan_output`（后台线程）顺带读：扫描本就逐文件 stat，读封面走 ffmpeg 子进程在同一后台线程完成，结果随 item 回传主线程。
   - 或更保守：**只在 `_make_card` 物化时懒读**——每张可见卡才起一次 ffmpeg，配合缓存。与现有懒加载架构最契合，首屏只处理十几张卡。
2. **缓存**：以 `path -> (mtime, QPixmap/bytes)` 做字典缓存；mtime 变化才重读（刷新时复用）。缩放后的 QPixmap 缓存比原图更省内存。
3. **无封面兜底**：ffmpeg 加 `-map 0:v:0?`；无图时显示占位相册图标（`FluentIcon.PICTURE` 或资源图），保持卡片高度一致。
4. **布局改动**：`TaskCard` 左侧插 `QLabel(setPixmap)`，宽度固定 ~48px、高度贴合 64px 行高；文件名/元信息区右移。注意 `MarqueeLabel` 的 `Ignored` 水平策略，避免封面把它撑宽。
5. **取消/竞态**：滚动很快时，物化出的读图请求可能被下一批重建取代；用代次号（类似 `_scan_gen`）或 `QPixmap` 缓存键判断，避免过时结果回填已销毁卡片。
6. **失败隔离**：非音乐文件、损坏文件、ffmpeg 异常一律静默回退占位图，不能让单张卡片的读图失败拖垮整页（参考现有扫描 `try/except OSError: continue` 的容错风格）。

## 五、性能与影响评估

| 维度 | 评估 |
|---|---|
| 首屏延迟 | 【静态】若懒读：首屏可见约 12~24 张卡，每张一次 ffmpeg（本地进程约几十毫秒），串行会累积到秒级；建议缓存 + 后台线程池并行，或分帧读取。 |
| 大列表 | 懒加载保证只有可见卡读图，千级文件与当前架构兼容；这是**必须**守住的约束，不能改成全量预读。 |
| 内存 | 缓存缩略图（48×48 RGBA≈9KB/张）；即使缓存上千张也仅 ~10MB 级，可控。切勿缓存原图（几 MB/张）。 |
| 打包 | 【静态】`build.py` 内嵌整个 `tools/`，ffmpeg 已在内，**无新增打包步骤/体积**；若选方案 B 则需改依赖并重打包。 |
| 平台 | ffmpeg 参数是跨平台写法；当前项目 Windows 专用，无额外适配。 |

## 六、风险与规避

| 风险 | 规避 |
|---|---|
| 大多数文件无内嵌封面 → 观感"功能没生效" | 明确占位图 + 提示来源说明；结合已有「更新封面」选项（联网补图）作为上游补充 |
| ffmpeg 进程开销 / 卡顿 | 懒读取（只物化可见卡）+ 缓存 + 后台线程 + 分帧，禁止全量同步读 |
| 滚动时过时结果回填已销毁卡片 | 代次号/缓存键校验，`deleteLater` 的卡片不接收异步结果 |
| 无损/冷门格式（ogg/ape/wv…）封面 | 当前实测覆盖 mp3/m4a/flac 主流格式；冷门格式回退占位图，不报错 |
| 新依赖 / 打包负担 | 选方案 A 即可完全规避 |

## 七、结论与建议路径

1. **立项建议**：值得做。零新增依赖、与现有懒加载架构天然契合，是"看起来像正经音乐库"的高性价比改进。
2. **推荐路径**：方案 A（ffmpeg 提取）+ 懒加载时按需读 + 缩略图缓存 + 占位图兜底；不动扫描主线程，不动 service 层。
3. **范围建议**：先做"内嵌封面读取与展示"这一件事；联网补图（um `--update-metadata`）沿用现有配置，不作为本功能的一部分绑定。
4. **验证边界**：本分析实测了 mp3/m4a/flac 的提取与 QImage 加载；ogg/ape/wv 等格式未实测，按"回退占位图"处理。
